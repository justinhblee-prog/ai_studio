# 복구 훈련 (RTO 측정) — R-077

`scripts/restore_drill.py`가 **백업 → 검증 → 새 빈 폴더로 복원 → 복원본 무결성 검사**를 한 번에 돌리고 단계별 시간을 JSON으로 냅니다. 운영 백업·운영 DB는 쓰지 않습니다(시험용 임시 환경만, 실제 환경은 `--db/--assets-dir`로 **읽기 전용 복사본**을 줄 때만).
```
python scripts/restore_drill.py --demo small        # 작은 시연 환경을 만들어 훈련
python scripts/restore_drill.py --demo scale        # 행 80,044개 · 파일 10,009개 규모
python scripts/restore_drill.py --db <복사본.sqlite3> --assets-dir <복사본 자산 폴더>
```
종료 코드 0 = 모든 검사 통과, 1 = 하나라도 실패. 백업은 SQLite 온라인 백업 API(WAL 안전)와 SHA-256 매니페스트를 쓰는 기존 `scripts/backup_restore.py`를 그대로 사용합니다.

## 복원본에서 확인하는 것
| 검사 | 통과 조건 |
|---|---|
| `integrity_check` | SQLite 무결성 `ok` |
| 외래 키 | `foreign_key_check` 위반 0 |
| 행 수 | **모든 표**의 행 수가 원본과 같음(다르면 표 이름과 두 값을 보고) |
| 자산 파일 | 삭제되지 않은 모든 자산 행의 파일이 있고 **크기·SHA-256이 DB 기록과 같음** |
| 응용 시험(시연 모드만) | 앱을 **복원본**에 연결해 라이브러리 목록과 저장된 그림 읽기가 성공 |
백업 단계의 검증은 **복원 전에** 매니페스트와 대조하므로 백업이 손상되면 복원 자체를 하지 않습니다(시험으로 확인).

## 측정치 (GitHub CI 러너 1대, 2026-11-17, 일반 SSD 아님·병렬 부하 있음 — 이 컴퓨터·운영 서버의 값이 아님)
| 환경 | DB 크기 | 파일 | 행 수 | 백업 | 검증 | **복원** | 검사 | 응용 시험 | **RTO** |
|---|---|---|---|---|---|---|---|---|---|
| small | 0.45MB | 18개 / 1.6KB | 72 | 0.01초 | 0.00 | 0.00 | 0.00 | 0.08 | **0.09초** |
| scale | **21.9MB** | **10,009개 / 0.23MB** | **80,044** | 1.01초 | 0.51 | **1.31** | 0.22 | 0.20 | **2.24초** |
**RTO 정의**: 검증 + 복원 + 무결성 검사 + 응용 시험(백업 시간은 복구 시간에 포함하지 않음).

## 읽는 법·한계(과장하지 않음)
- **scale의 파일은 아주 작습니다(합계 0.23MB)**. 실제 사진은 한 장에 수백 KB~수 MB라 **복원 시간은 파일 총 용량에 비례해 훨씬 길어집니다** — 이 표의 2초는 "행 8만 개와 파일 1만 개를 다루는 데 걸리는 고정 비용"이지 운영 RTO가 아닙니다. 운영 용량(예: 사진 50GB)의 RTO는 **같은 방식으로 복사본을 만들어 측정해야 하며 아직 측정하지 못했습니다(미실행)**.
- 측정은 **같은 디스크 안에서의 복사**입니다. 원격 저장소(Supabase 등)에서 내려받는 시간은 포함되지 않습니다.
- **복원 뒤 서비스를 다시 띄우는 시간, DNS·환경 변수 전환, 사람이 판단·승인하는 시간**은 RTO에 없습니다.
- **RPO**(마지막 백업 이후 잃는 데이터)는 백업 주기가 정하며 이 훈련으로 측정하지 않습니다. 백업을 **누가 언제 자동으로 돌리는지**는 이 저장소에 정해져 있지 않습니다(운영 결정).
- 생성 DB가 자산 DB와 **따로 있는 환경**은 이 훈련이 한 DB만 다룹니다(미지원).
- PostgreSQL 경로는 비활성이라 **해당 없음**.
