# 버전 및 문서 관리 규칙

## 1. 서로 다른 번호를 분리합니다

| 식별자 | 형식 | 목적 | 증가 기준 |
|---|---|---|---|
| 제품 버전 | `MAJOR.MINOR.PATCH` (SemVer) | 외부에 제공하는 제품 릴리스 호환성 | 실제 제품 릴리스 시점 |
| 엔지니어링 빌드 ID | `BUILD-00001` | 개발 스냅샷·테스트·ZIP의 추적 | 재현 가능한 소스 스냅샷을 만들 때마다 1 증가 |
| 문서 정책 버전 | 문서 내부 `1.0` 등 | 이 문서 관리 규칙 자체 | 정책 구조가 바뀔 때만 변경 |
| ADR 번호 | `ADR-0001` | 변경하지 않을 의사결정 기록 | 새 의사결정마다 1 증가 |

현재 제품 버전은 아직 지정하지 않습니다. 과거의 `v0.11`~`v0.81` 형식은 당시 엔지니어링 스냅샷 번호로 취급하며, SemVer 제품 릴리스로 소급 해석하지 않습니다.

## 2. 빌드 ID 규칙

- 현재 기준은 `BUILD-00117`입니다.
- 코드 변경 또는 문서 관리에 영향을 주는 재현 가능한 스냅샷을 만들면 다음 번호를 사용합니다.
- 빌드 ID는 단조 증가하며 재사용하지 않습니다.
- ZIP 이름은 `AI_CREATOR_STUDIO_BUILD-00081_<scope>.zip` 형식을 사용합니다.
- ZIP 안의 `BUILD_INFO.md`에는 빌드 ID, 기반 빌드, 생성 목적, 검증 결과, SHA-256을 기록합니다.
- 빌드 ID만으로 제품 기능 완성도나 배포 가능성을 의미하지 않습니다.

## 3. 문서별 수명주기

### 상시 최신 문서(단일 파일)

- `README.md`: 프로젝트 진입점
- `docs/handoff/CURRENT_HANDOFF.md`: 최신 인수인계
- `docs/CHANGELOG.md`: 변경 요약 누적
- `docs/development/DEVELOPMENT_LOG.md`: 개발 상세 이력 누적

상시 최신 문서는 같은 경로에서 갱신합니다. `handoff_v5_41`, `handoff_v5_42`처럼 매번 별도 번호 파일을 만들지 않습니다. 과거 상태는 Git 이력과 개발 로그/빌드 기록으로 추적합니다.

### 고정 문서

- `docs/releases/BUILD-xxxxx.md`: 릴리스 또는 감사/배포 후보로 고정할 빌드에서만 생성합니다.
- `docs/decisions/ADR-xxxx.md`: 결정의 맥락·선택지·결과를 고정 기록합니다.
- `docs/archive/legacy_snapshots/`: 이전 문서 파일을 원형 보존합니다.

## 4. 문서 작성 원칙

- README에는 프로젝트 사용법과 진입점만 둡니다. 매 빌드의 상세 변경 기록을 복제하지 않습니다.
- CHANGELOG는 사용자가 이해할 수 있는 변경 요약을 기록합니다.
- DEVELOPMENT_LOG는 변경 파일/동작, 테스트 명령, 결과, 제한 사항을 기록합니다.
- CURRENT_HANDOFF는 현재 기준 소스, 검증 상태, 알려진 위험, 다음 작업만 유지합니다.
- 테스트를 실행하지 않았으면 통과라고 쓰지 않습니다. 테스트 범위와 환경을 함께 씁니다.
- 구현하지 않은 기능은 `미구현`, 환경 때문에 확인하지 못한 것은 `미검증`, 의사결정이 필요한 것은 `결정 대기`로 구분합니다.
- 빌드 번호와 제품 버전을 혼용하지 않습니다. 제품 버전은 첫 외부 릴리스 기준을 정한 뒤 SemVer로 부여합니다.

## 5. 이전 문서의 처리

- 기존 `README_v*.md`, `개발진행기록_v*.md`, `handoff_*_v*.md`는 `docs/archive/legacy_snapshots/`에 원본 그대로 보존합니다.
- 기존 번호를 다시 매기거나 내용을 소급 수정하지 않습니다.
- 과거 문서의 `v0.xx`는 레거시 스냅샷 ID이고 `v5.xx`는 레거시 인수인계 파일명일 뿐, 상호 비교 가능한 버전 체계가 아닙니다.
