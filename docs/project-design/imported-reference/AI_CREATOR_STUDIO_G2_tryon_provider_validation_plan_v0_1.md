# AI CREATOR STUDIO — G2 실제 AI Try-on Provider 검증 계획

- 문서 버전: v0.1
- 기준일: 2026-11-02
- 상태: 실행 준비안 / 개발자 검토 및 제품 책임자 승인 전
- 상위 기준: `AI_CREATOR_STUDIO_integrated_execution_baseline_v0_2.md`
- 관련 기준: `AI_CREATOR_STUDIO_technical_architecture_implementation_v0_2.md`, `AI_CREATOR_STUDIO_developer_kickoff_spec_v0_2.md`, 기존 Try-on PoC v0.2 설계
- 선행 Gate: G0 저장소·코드 감사
- 범위: 이미지 기반 AI Virtual Try-on 실제 Provider 1개 이상 호출 및 결과·비용·품질 증거 확보

> 이 문서는 실행 계획입니다. Provider 계정 연결, 실제 API 호출, 결과 품질, 비용, 상업 이용 가능성은 아직 확인되지 않았습니다. 계획 작성만으로 G2 구현 또는 통과를 선언하지 않습니다.

## 1. 목적과 통과 질문

G2는 다음 질문에 실제 증거로 답하는 단계입니다.
1. 권리 확인된 사람 기준 이미지와 개별 의류 이미지를 실제 Provider에 전달할 수 있는가?
2. 실제 요청이 Provider에 접수되고, 상태 조회 또는 완료 응답을 통해 결과를 회수할 수 있는가?
3. 결과 이미지가 내부 Asset/AssetVersion으로 안전하게 저장되고 원본 입력과 연결되는가?
4. 동일 입력의 품질·성공률·지연·실제 원가를 재현 가능한 방식으로 측정할 수 있는가?
5. 데이터 사용, 보존, 삭제, 학습 이용, 상업 이용 등 공급자 정책을 검토할 수 있는가?

## 2. 범위와 제외

### 포함
- 첫 Provider Adapter 1개 실연동. 기존 설계의 FASHN Try-On v1.6을 후보로 검토하되, 현재 지원 버전·API 계약·가격·정책을 공급자 공식 자료로 재확인한 뒤 선택한다.
- 동일 조건 비교가 가능하면 두 번째 후보(예: FASHN Try-On Max 또는 fal.ai 경유 후보)를 추가하되, 첫 Adapter의 재현 가능한 실행을 우선한다.
- 기준 모델 이미지 1장, 개별 의류 이미지 3~5장. 최초 시험은 상의 중심으로 범위를 제한한다.
- 비동기 Job 제출/상태 조회/결과 회수, 결과 파일 영속 저장, 메타데이터 및 원가 기록.
- 공급자명을 가린 블라인드 품질 평가.

### 제외
- 3D Garment Simulation, 패턴·메시 피팅, GLB Viewer의 기능 검증.
- Photo Engine의 독립적인 후처리 품질 검증.
- 영상 생성, 대규모 배치, 고객 대상 SLA 보장.
- Mock 결과를 실제 Provider 통과 증거로 인정하는 것.
- 공급자 약관 검토 전 고객 원본 이미지 또는 민감한 개인정보를 무단 전송하는 것.

## 3. 선행 조건 및 실행 승인

G2 실호출 전에 다음을 확인한다.
- [ ] G0 증거 패키지 검토 및 기존 Provider 관련 코드/Adapter 재사용 판정
- [ ] Provider 공식 문서에서 API 버전, 입력 필드, 파일 형식·크기·해상도 제한, 비동기 상태 조회, 오류 코드 확인
- [ ] API 키는 Secret Manager 또는 동등한 비밀 저장소에 보관하고 로그·프런트엔드·문서에 노출하지 않음
- [ ] 공급자 약관 및 데이터 처리 조건 검토: 입력·출력 보존기간, 삭제 방법, 모델 학습 이용 여부/옵트아웃, 하위 처리자, 처리 지역, 상업 이용, 금지 콘텐츠
- [ ] 사람 기준 이미지 및 의류 이미지의 권리·동의·사용 목적·기간 확인
- [ ] 테스트 예산 상한과 호출 횟수 상한을 제품 책임자가 승인
- [ ] 원본/결과 파일 저장 위치, 접근 권한, 보존·삭제 담당자 지정
- [ ] 실제 호출 전 비밀키·개인정보 마스킹과 감사 로그 정책 점검

선행 조건이 충족되지 않으면 실제 호출을 보류하고 차단 사유와 책임자를 기록한다.

## 4. 테스트 입력 데이터셋

### 4.1 기준 모델 이미지
- 권리 및 사용 동의가 확인된 이미지 1장.
- 한 명의 인물이 전신 또는 상반신으로 명확히 보이고, 가림·왜곡·강한 필터가 최소화된 사진.
- 입력 원본의 해시, 파일 형식, 크기, 해상도, 출처/권리 기록을 남긴다.
- 실제 사람 이미지 사용이 승인되지 않은 경우, 사용 권리가 명확한 합성 모델 이미지를 사용하고 그 사실을 기록한다.

### 4.2 의류 이미지
- 개별 의류 이미지 3~5장. 콜라주·시트·여러 상품 합성 이미지는 실제 API 입력으로 사용하지 않는다.
- 최초 시험은 상의 카테고리로 통일하고, 정면 제품 이미지 중심으로 구성한다.
- 각 이미지에 SKU/상품 식별자, 출처, 권리, 배경, 촬영 방향, 파일 메타데이터를 기록한다.
- 색상·프린트·로고·단추·카라·소매·기장 등 디자인 식별 요소가 보이는 입력을 우선한다.

### 4.3 입력 고정 및 재현
- 동일 Provider 비교 시 동일한 모델 이미지와 동일한 의류 이미지를 사용한다.
- Provider별 필수 파라미터 차이는 별도 기록하고, 조정이 필요한 경우 원본 설정과 변경 이유를 보존한다.
- 입력 파일은 수정하지 않고 원본 해시와 AssetVersion을 고정한다.

## 5. 실행 시나리오

1. 입력 권리 및 파일 검증
2. 테스트 케이스 ID 발급 및 입력 AssetVersion 고정
3. Provider/Model/Capability/Policy 선택 근거 기록
4. 요청 검증 및 비용 견적(가능한 경우) 산출
5. 승인된 테스트 예산 내에서 실제 Provider 요청 제출
6. Provider request ID 및 내부 Job/Execution ID 연결
7. 비동기 상태 조회 또는 webhook 처리
8. timeout/불명확한 응답이면 Provider request ID로 상태를 재확인하고 중복 제출 금지
9. 결과 파일 다운로드 및 악성/형식/크기 검증
10. Object Storage 영속 저장 및 AssetVersion/GenerationResult 생성
11. 실제 청구 단위·요금·호출량·재시도 비용을 기록
12. 블라인드 품질 평가 및 결과 비교
13. 실패·취소·삭제 요청·재실행 이력을 기록

## 6. 최소 시험 행렬

| ID | 시험 | 최소 조건 | 증거 |
|---|---|---|---|
| G2-01 | 정상 실제 호출 | 고정 모델 이미지 + 의류 1종 | Provider request ID, 시간, 결과 파일 |
| G2-02 | 입력 변형 | 동일 모델 + 의류 3~5종 | 각 입력/출력 AssetVersion 연결 |
| G2-03 | 비동기 상태 | 접수부터 완료까지 상태 기록 | 상태 이벤트 및 타임스탬프 |
| G2-04 | 결과 영속화 | 결과 다운로드 후 저장 | 저장 객체 식별자, checksum, DB 참조 |
| G2-05 | 실패 응답 | Provider 오류 응답 정규화 | 오류 코드/메시지 마스킹 및 Job 상태 |
| G2-06 | timeout/결과 불명 | 요청 접수 후 클라이언트 timeout 상황 재현 또는 안전한 시뮬레이션 | 중복 제출 방지, request ID 조회 기록 |
| G2-07 | 재시도 | 정책상 재시도 가능한 오류만 제한적으로 수행 | attempt 번호, 원인, 추가 비용 |
| G2-08 | 취소 | Provider가 취소를 지원하는 경우 검증 | Provider 취소 결과와 내부 상태 구분 |
| G2-09 | 권한/비밀정보 | 비인가 사용자 접근 및 로그 점검 | 403 등 접근 증거, 키 미노출 확인 |
| G2-10 | 삭제/보존 | 공급자·내부 저장소 삭제 절차 확인 | 삭제 요청/완료 증거 또는 정책상 제한 기록 |

실제 API가 지원하지 않는 기능은 억지로 통과 처리하지 않는다. 예를 들어 Provider 취소 API가 없으면 `미지원`으로 기록하고 내부 취소 처리와 과금 여부를 별도로 검증한다.

## 7. 품질 평가 프로토콜

공급자명을 숨기고 동일한 평가표로 결과를 검토한다. 각 항목은 1~5점으로 평가하되, 평가자·평가일·판정 근거를 남긴다.

| 평가 항목 | 관찰 기준 |
|---|---|
| 의류 디자인 보존 | 실루엣, 카라, 소매, 단추, 프린트, 로고, 색상, 패턴의 유지 |
| 착장 자연스러움 | 신체와 의류의 접촉, 주름, 중력 방향, 경계의 자연스러움 |
| 모델 일관성 | 얼굴·헤어·체형·피부·포즈의 불필요한 변화 |
| 이미지 결함 | 손/팔/목/의류 경계, 왜곡, 중복 부위, 텍스트/로고 오류 |
| 상품 표현 적합성 | 전자상거래 상세페이지/룩북에 쓸 수 있는 수준인지 |
| 재현성 | 동일 조건 반복 시 품질 편차와 실패 빈도 |

- 점수만으로 자동 승자를 선언하지 않는다. 중대한 상품 디자인 왜곡은 평균 점수와 별개로 치명 결함으로 표시한다.
- 최소 2명의 평가자가 가능하면 독립 평가하고, 불일치는 근거를 기록해 합의한다.
- 시험 표본이 작으면 통계적 일반화나 성공률 보장을 하지 않는다.

## 8. 성능·비용 기록

각 실행마다 다음을 기록한다.
- Provider / Model / API version / capability 및 요청 파라미터
- 내부 Job ID / Execution ID / Provider request ID
- 입력 AssetVersion ID 및 해시
- 요청 제출, 접수, 완료, 결과 다운로드, 저장 완료 시각
- 총 지연시간과 각 단계 지연시간
- 성공/실패/부분 성공 및 정규화 오류 코드
- 재시도 횟수, 취소 여부, Provider 청구량
- 공식 가격표 기준 예상 비용과 실제 청구/사용량 근거
- 환율/세금/최소 과금/크레딧 차감은 구분해서 기록
- 결과 파일 크기, 해시, 저장 위치 식별자

가격표만으로 실제 원가를 확정하지 않는다. 청구 내역 또는 공급자 사용량 데이터가 없으면 `예상 비용`으로 표시한다.

## 9. 내부 데이터 및 상태 계약

기존 공통 Job 시스템을 재사용하며 Try-on 전용으로 중복 Job 시스템을 만들지 않는다.

필수 연결 관계:
- Project → Input Assets/AssetVersions
- GenerationJob(job_type = TRY_ON) → JobExecution(s)
- Provider / Model / Capability / Policy snapshot
- Provider request ID ↔ 내부 Execution ID
- GenerationResult → Output AssetVersion
- UsageRecord / Cost record / Credit Ledger reference
- JobEvent / AuditEvent

상태 원칙:
- 검증 및 권한 확인 전 비용 예약 금지.
- 크레딧 예약이 필요한 경우 예약 성공 전 Provider 큐에 넣지 않음.
- Provider timeout은 Provider 실행 실패와 동일하다고 단정하지 않음.
- 실제 결과 파일 영속 저장 및 DB 연결이 끝나기 전에 `SUCCEEDED`로 전환하지 않음.
- 재시도는 attempt 이력과 비용을 남기며 중복 과금을 방지.
- 공급자 취소 성공과 내부 Job 취소 상태를 구분.
- 비밀키, 서명 URL, 원본 개인정보를 로그에 남기지 않음.

## 10. 권리·보안·개인정보 체크

- 입력 이미지의 저작권/초상권/상업 이용 허가 증빙 보관.
- 실제 인물 이미지의 동의 범위와 철회/삭제 요청 절차 확인.
- Provider의 입력·출력 보존 및 학습 이용 정책 확인.
- 저장/전송 암호화, 최소 권한, 접근 감사, 만료 URL 적용.
- 로그와 보고서에는 토큰·키·개인 식별 정보·원본 이미지 URL을 제거.
- 데이터 처리 지역 및 국외 이전 이슈는 대상 국가와 공급자 계약을 확인한 뒤 법무 검토 대상으로 분리.
- 정책 검토가 끝나지 않은 공급자는 고객 데이터에 사용하지 않음.

## 11. G2 통과 기준

다음 항목이 모두 증거로 확인되어야 G2 통과를 제안할 수 있다.
- [ ] 실제 Provider API 요청이 최소 1회 성공했고, Provider request ID가 확인됨.
- [ ] 고정 입력과 결과 파일이 재현 가능한 방식으로 연결됨.
- [ ] 결과가 내부 저장소에 영속 저장되고 AssetVersion/GenerationResult 참조가 확인됨.
- [ ] 비동기 상태·오류·timeout/중복 방지 동작이 기록됨.
- [ ] 품질 평가표가 작성되었고 치명 결함이 명시됨.
- [ ] 지연시간 및 실제 원가 또는 실제 사용량 근거가 기록됨. 근거가 없는 금액은 예상치로 분리됨.
- [ ] 권리·상업 이용·데이터 보존/삭제/학습 정책 검토 결과가 기록됨.
- [ ] 비밀키·개인정보 노출이 없고 권한 검사가 확인됨.
- [ ] 실행 환경, commit, 실행 명령, 테스트 로그, 담당자 및 승인자가 기록됨.

실제 API 호출만 성공하고 결과 저장·권리·비용·품질 근거가 빠진 경우 G2는 부분 완료 또는 차단 상태이며 통과가 아니다.

## 12. 제출 증거 패키지

개발자는 아래 자료를 하나의 제출 패키지로 제공한다.
1. 저장소 URL(접근 가능한 경우), branch, commit hash, 실행 명령
2. Provider 공식 API 문서 링크/확인일/API version
3. 마스킹된 request/response metadata 및 Provider request ID
4. Job/Execution/Event 로그와 상태 전이
5. 원본 입력 파일 식별자·해시·권리 기록
6. 결과 이미지 및 결과 파일 checksum/저장 참조

## 부록 B. 판정 용어

- `준비 완료`: 검증 절차와 제출 기준이 문서화됨.
- `실행 중`: 실제 구현 또는 호출이 진행되고 증거가 생성되는 중.
- `부분 완료`: 일부 증거는 있으나 Gate 통과 기준을 모두 충족하지 못함.
- `증거 대기`: 실행 여부를 판단할 근거가 제출되지 않음.
- `차단`: 선행 조건/권한/정책/기술 문제로 안전한 실행이 불가능함.
- `통과`: 모든 필수 기준과 증거를 검토하고 승인자가 승인함.
